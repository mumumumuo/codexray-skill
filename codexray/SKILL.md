# CodeXray 多 Agent 并行审计

系统性白盒审计流程，源自 CodeXray 平台的多 Agent 编排逻辑。**没有静态预扫** —— 攻击面靠 Phase 1 架构理解摸清，漏洞靠 Phase 2 七个域子 Agent **并行**深度审计，结论靠 Phase 3 复核兜底。编排者（主 agent）自己不深读业务代码，只做派发、回收、去重、复核、写报告。

```
开工（cp 模板建报告骨架）
  └─ Phase 1 架构理解（1 个架构子 agent：技术栈/路由/中间件）
       └─ Phase 2 分域并行审计（7 个域子 agent，同一条消息一次性派发）
            └─ Phase 3 复核与攻击链（误报过滤/去重/定级复核/缺口审查/链组合）
                 └─ 收尾（唯一产物：一个 HTML 报告）
```

## 命令与调用

```
/codexray d <目标路径>
```

- `d` 也接受 `-d` 写法。目标路径是**被审项目的根目录**
- 带路径调用 → 解析后直接开扫，不要复述用法
- 无参数 `/codexray` → **不要开始审计**，先输出使用说明（命令格式 + 示例 `/codexray d D:\web` + 流程三阶段一句话），等用户给出路径
- `d` 缺失（只给了路径）→ 直接开扫
- **自然语言触发**（"帮我审计下 D:\xxx 这个项目"）→ 从描述中取路径直接开扫；用户指定只审某几类漏洞（如"只看注入和越权"）时仅派发对应域（合法域：`rce` / `injection` / `file` / `auth` / `business` / `xss` / `config`，中文别名映射后执行），Phase 1 与 Phase 3 照常执行
- 路径猜不出来 → 问用户，不要猜

**输出语言：中文**。漏洞标题、描述、分析、修复建议、定级理由都用中文。代码片段、HTTP 数据包、文件路径等技术标识符保持原样。

## 运行前提

| 能力 | 用途 | 缺失时的退路 |
|---|---|---|
| 读文件 / 检索内容（Grep 类） | 追调用链（子 agent 与编排者都需要） | **必需**，无法替代 |
| 执行 shell 命令 | `cp` 模板、清理临时文件 | **必需** |
| 写/改文件 | 生成与增量更新 HTML 报告 | **必需** |
| 启动并行子 agent | Phase 1 架构理解、Phase 2 七域并行 | 见下方降级方案 |
| 任务清单 | 进度可视化 | 缺失时跳过，不影响流程 |

**没有子 agent 能力时的降级**（唯一实质改变执行方式的一项）：

- Phase 1 架构理解由编排者在主上下文完成（按 [architect.md](references/architect.md) 的清单执行，预算按下限）
- Phase 2 改为**串行逐域**审计，每域按域参考文件执行。此时上下文压力极大，必须严格执行「读 3-5 个文件 → 立即产出 finding → 提交进报告 → 再下一条链」，**每个域审完立刻把结论写进报告文件再开始下一个域**
- 串行执行在最终输出追加一行：`提示：本次串行执行，后段域深度可能低于前段`

**skill 目录**：本 SKILL.md 所在目录记为 `SKILL_DIR`。下文所有 `references/...` 相对路径、`cp` 模板命令都以 `SKILL_DIR` 为根解析；若 shell 变量未注入，直接用 skill 目录的绝对路径。

## 工作节奏（重要）

**不要陷入「无限读文件」模式。** 正确的节奏是每追踪完一条调用链就立即产出结论：

```
读 3-5 个文件（追踪一条调用链）→ 分析 → 产出 finding → 读下一条链
```

连续读几十个文件再统一输出，会把上下文烧光却没有产出。路由与架构情报是起点，不是范围上限 —— 主动向外扩展，但每条链追完先落结论。

## 开工顺序（解析完参数后的两件事）

1. **建任务清单** —— 按「执行期任务清单」一节建阶段任务
2. **`cp` 出报告骨架** —— 复制模板、填头部 meta、删占位卡片（见「报告」第 1 步）

合计一次 `cp` + 一两次 Edit，零成本。**报告文件必须先于第一条结论存在** —— 否则实际执行时会退化成扫完再统一生成。

## 执行期任务清单

审计一开始就建任务清单，让用户随时看得到跑到哪了。清单是**进度的唯一载体** —— 有它就不要在对话里播报「正在派发」「XX 域返回了」。

```
□ 开工准备（cp 模板 + 建报告骨架）
□ Phase 1 架构理解（技术栈 / 路由 / 中间件）
□ Phase 2 分域并行审计
□ Phase 2 └ rce 域审计
□ Phase 2 └ injection 域审计
□ Phase 2 └ file 域审计
□ Phase 2 └ auth 域审计
□ Phase 2 └ business 域审计
□ Phase 2 └ xss 域审计
□ Phase 2 └ config 域审计
□ Phase 3 复核与攻击链（误报 / 合并 / 定级 / 缺口 / 链组合）
□ 报告收尾
```

状态更新纪律：

- 解析完参数先建「开工准备 / Phase 1 / Phase 2 / Phase 3 / 报告收尾」五个阶段任务并建好七个域子任务（仅派发实际执行的域）
- 进入一个阶段先标 `in_progress`，做完立刻标 `completed`，不要攒着一起标
- 派发那一刻把全部域子任务一起标 `in_progress` —— 它们是并行跑的
- 某域返回**且卡片已插进报告**才标该域 `completed`
- 全部域子任务完成后才标 Phase 2 完成；报告自检过完才标「报告收尾」完成

## Phase 1 — 架构理解（1 个架构子 agent）

派发**一个**只读子 agent（Agent 工具，`subagent_type` 取 `Explore`），做全面架构理解：技术栈识别、路由发现、中间件链。结果通过返回消息带回，**不落盘任何文件**。

**派发 prompt 固定按此模板**（尖括号占位符派发时替换）：

```
你是源码安全审计的架构理解子代理，只做架构理解，不做漏洞审计。
项目根路径：<PROJECT_PATH>

先 Read 并严格遵循 <SKILL_DIR>/references/architect.md —— 这是你的权威指令：
任务范围（技术栈/路由/中间件 3 件事）、按框架选 Grep pattern、读文件纪律、
返回格式都在里面。特别注意其中的「严格禁止」清单 —— 不要 grep 危险 sink、
不要搜配置问题、不要追源-汇路径、不要输出 finding。

按该文件规定的返回格式把全部架构信息写进你的返回消息（纯文本，不写任何文件），
最后一行输出 ARCHITECT_SCAN_COMPLETE。
```

编排者拿到返回消息后做两件事：

1. **编辑报告架构概览**：把技术栈（带版本）/ 认证机制 / 数据源 / 用户输入入口 / 架构摘要 / 目录结构 / 中间件 / 端点列表直接 Edit 进报告右栏（写法见「报告」第 2 步）
2. **组装 Phase 2 注入上下文**：在上下文里把架构信息整理成各域共用的「项目架构概要」（见 Phase 2 派发模板）

**失败降级**：架构子 agent 失败、超时或返回不完整（缺路由清单或缺框架版本）→ 编排者自己在主上下文按 architect.md 清单补跑（预算按下限），补不齐的字段在报告里写「未采集」。**不要因为这一步失败就中断审计。**

## Phase 2 — 分域并行审计（7 个域子 agent，硬性要求）

Phase 2 由**编排者 + 七个域子 agent** 执行。主 agent 是编排者，**自己不深读业务代码**（只做派发、回收、去重、写报告）。这是硬性要求，不是建议 —— 串行逐域审计会把主上下文在 2-3 个域后烧光，后面的域根本审不到。

### 派发前：编排者构建各域上下文（注入式）

派发不是发一句「去审 XX 域」。编排者从 Phase 1 架构信息里为每个域组装工作上下文，**直接注入子 agent 的 prompt** —— Phase 1 的成果喂到嘴边：

- **公共架构情报**（每个域的 prompt 都带）：框架/语言（带版本）、认证机制、数据源、用户输入入口、目录结构（≤2000 字符）、中间件链
- **端点清单**（每个域的 prompt 都带）：`METHOD PATH — 处理函数 [鉴权] — 描述`，超过 120 条截断并注明「已截断 N 条，按需读路由注册文件」

**规划判断**（编排者自己一次做完，不单独起规划 agent）：默认七域全启用；只有项目结构清楚地不涉及该领域时才跳过（如纯 CLI 工具无路由 → auth 可跳、纯 API 无前端渲染 → xss 可跳），**最多跳 2 个**，跳过的域在最终输出的「分域」一行写 `跳过:<理由>`。**不要因为「没看到相关线索」就跳过** —— 没有 Phase 1 线索的域仍要派发，在 prompt 里注明「架构情报中无本域强线索，从路由清单和域参考文件的关键函数名自行检索」。

### 派发（并行）

**全部域必须在同一条消息里一次性发出全部子 agent 调用**（全量是 7 个，限定域是所选的 N 个），严禁等一个返回再发下一个 —— **并行是这一阶段的全部意义**。派发前把各域子任务一并标 `in_progress`。

子 agent 需要的能力是**读文件 + 检索内容**，不需要写文件（返回纯文本，由编排者编辑进报告）。用 Agent 工具、`subagent_type` 取 `Explore`。无子代理能力时按「运行前提」降级串行。

**派发 prompt 固定按此模板**（尖括号占位符派发时替换为实际内容）：

```
你是 <域> 域的源码安全审计子代理，只审这一个域，不要越界。
项目根路径：<PROJECT_PATH>

先 Read 并严格遵循这两个文件：
1. <SKILL_DIR>/references/domains/<域>.md —— **本域的权威检查清单**。含「审计范围」
   「任务要求」「判定纪律」「边界」，通读全文，从中提取本域关键函数名作为 Grep 检索词
2. <SKILL_DIR>/references/finding-schema.md —— 字段 schema、定级纪律、POC 要求

## 项目架构概要（Phase 1 已搜集，你的工作输入）
框架/语言：<带版本>
认证机制：<auth_mechanism>
数据源：<data_sources>
用户输入入口：<entry_points>
目录结构：
<截断至 2000 字符的目录树>
中间件：
<名称 | scope | 职责，逐条>

## 端点清单（Phase 1 已搜集）
<METHOD> <path> — <处理函数> [鉴权] — <描述>
（逐条；超过 120 条注明已截断）

## 审计要求
1. 基于上方情报自主决定读哪些文件：先从域参考文件的关键函数名对本项目做一轮本域
   Grep 检索定位 sink，再逐端点/逐 sink 追调用链排查（如 auth 域：逐条路由核对认证
   中间件与处理器内的鉴权逻辑）
2. 情报只是起点不是范围上限 —— 架构情报没标 ≠ 没有。封装调用、动态拼接、间接数据
   流都要靠你自己追链发现
3. 节奏：读 3-5 个文件追完一条调用链 → 立即产出一条 finding → 再追下一条，禁止连续
   读几十个文件后才输出
4. 域边界：审到其他域的漏洞不要输出 finding，记为越界线索（位置 + 现象 + 建议归属域）
5. 定级看实际影响不看类型；可触发类必须给 raw HTTP POC 与预期响应；安全的代码不要
   包装成 finding

**输出语言：中文。** 漏洞标题、描述、定级理由、修复建议、覆盖度小结都用中文；
代码片段、HTTP 数据包、文件路径、函数名等技术标识符保持原样。

返回格式（纯文本，不要写 HTML、不要修改任何文件）：
- FINDINGS：每条按 finding-schema 全字段输出（vuln_type/severity/confidence/title/
  file_path/line_number/min_privilege/description/severity_reason/code_trace 四要素/
  evidence/poc/expected_result/fix_suggestion），一条一节，字段齐全
- COVERAGE：覆盖度小结（检查了什么、没审到什么；已完整覆盖要写明「已完整覆盖」）
- CROSS：越界线索（无则写无）
```

七个域各有独立的检查清单、追踪要点和判定纪律：

| 域 | 说明 | 参考 |
|---|---|---|
| `rce` | 命令执行、代码注入、反序列化、SSTI、表达式语言 | [rce.md](references/domains/rce.md) |
| `injection` | SQL / NoSQL / LDAP / XPath 注入 / XXE（含 Excel/OOXML 导入） | [injection.md](references/domains/injection.md) |
| `file` | 文件上传下载、路径遍历、zip slip | [file.md](references/domains/file.md) |
| `auth` | 未授权访问、认证绕过、水平/垂直越权、注册提权 | [auth.md](references/domains/auth.md) |
| `business` | 业务流程绕过、金额篡改、条件竞争、SSRF、幂等性 | [business.md](references/domains/business.md) |
| `xss` | 反射型、存储型、DOM 型 XSS | [xss.md](references/domains/xss.md) |
| `config` | 硬编码凭证、CORS、TLS、调试模式、组件 CVE | [config.md](references/domains/config.md) |

**域边界必须守住**（[domain-boundaries.md](references/domain-boundaries.md)）：七域范围不重叠，审 A 域看到 B 域的漏洞不输出 finding、记越界线索。越界输出会让同一漏洞重复报告、每个域失焦。

### 回收与提交

- 子 agent 返回后立即处理：跨域重复的就地去重（同一 `file:line` + 同一 sink/路由语义只保留描述最详细的一条）、按 severity 统一编号（按 rce→injection→file→auth→business→xss→config 顺序依次分配 V-001…，避免多个域都用 V-001）、按「报告」第 3 步的卡片写法插入报告 —— **收一个域提交一个域**，不必等七个全部返回
- 子 agent 之间看不到彼此的输出，跨域重复 finding 属正常；深度合并（同位置同语义的合并、call_chain 视角合并）留给 Phase 3 统一做
- 某域返回零 finding：COVERAGE 写明「已完整覆盖」→ 最终输出记 `0(已覆盖)`；覆盖不足 → 记 `0(缺口)` 并列入「缺口」块，两者必须区分

## Phase 3 — 复核与攻击链组合

七域全部返回且卡片进报告后，编排者在主上下文统一复核（输入都在你上下文里：Phase 1 架构信息 + 各域 FINDINGS/COVERAGE/CROSS）。**先 Read [review-rules.md](references/review-rules.md)** —— 那是本阶段的权威清单，按顺序做五件事，一步不能省：

1. **误报过滤** —— 逐条对照该漏洞类型的全部必要条件（review-rules.md 有每类的条件清单与常见误报模式），缺任一条标误报
2. **跨域去重** —— 同位置 + 同粗类别 + 同 sink/路由语义合并，保留最详细描述，合并 call_chain
3. **定级复核** —— 重新评估 severity，补全 severity_reason 与 expected_result；严禁按类型机械套高危
4. **覆盖缺口审查** —— 对比 Phase 1 攻击面 vs 实际覆盖，产出缺口清单
5. **攻击链组合分析** —— 至少尝试识别 1-3 条组合链；确实没有则说明原因

**复核是已有 finding 的审查者，不是新的产出者**：只做 keep（可调 severity/confidence）/ drop（标误报）/ merge（合并），严禁新增 finding、严禁重写 POC/evidence/description 等字段。

复核决策直接落到报告上（卡片怎么改、误报视图与攻击链视图怎么写，见 review-rules.md 末节与「报告」第 4 步）。

## 报告（实时提交的交互式 HTML，唯一产物）

报告输出为**单个完整自包含的交互式 HTML 文件**（白色主题），布局与前端交互严格遵循 [report-template.html](report-template.html)。头部 meta 的「模式」字段固定写「全量扫描」（限定域时写「自定义域扫描(列出所选域)」）。

**实时提交原则：报告不是扫完后一次性生成，而是边审边写。** 报告**文件在审计第一步就建好**（`cp` 模板），内容随审计推进增量填入：架构概览在 Phase 1 返回后填，finding 确认一条提交一条，攻击链和误报在 Phase 3 复核后提交。页面 JS 每次打开都会从卡片 DOM 自动重算计数/汇总/清单表/修复列表，**增量追加不需要同步改任何统计数字**。

**唯一产物原则：运行目录的最终交付物只有报告 HTML 一个文件。** finding 直接 Edit 进 HTML，**禁止先聚合成 JSON 再用脚本批量生成** —— 卡片是正文内容 + 既定模板片段拼出来的，直接编辑即可。审计过程产生的任何临时文件（`_*.txt`、`_*.py`、日志）收尾时全部删除。

提交时序：

1. **开工时就 `cp` 出报告骨架** —— 先复制再填，不要重写：

   ```bash
   cp "${SKILL_DIR}/report-template.html" "安全审计报告-<项目名>.html"
   ```

   落到当前工作目录。项目名取目标路径的目录名。**严禁用 Read 模板全文 + Write 重新生成** —— 模板约 4.7 万字符，读进来再写出去要烧掉近 3 万 token，且 CSS/JS 一旦丢字符整个报告的筛选与计数就失效。`cp` 是零成本且字节一致的。

   复制完成后立刻做两件不依赖审计结果的事：头部 meta 填好模式/项目/创建时间（「完成时间」暂留占位），**删除 #vulnList / #chainsView / #fpView 中的示例占位卡片**（保留各视图的插入锚点注释 `<!-- ══════════ ... 块结束 ══════════ -->`）。这样从第一条 finding 起就有地方落。

2. **Phase 1 返回后填架构概览**：用 Edit 把右栏架构概览全量填入 —— 框架/语言（带版本）/ 认证机制 / 数据源 / **用户输入入口**（顿号分隔，未采集时写「未采集」）/ arch-desc（架构摘要）/ 目录结构 / 中间件 / 端点列表（每端点一个 endpoint-item，method 类名 method-get/post/put/patch/delete，无认证用 route-auth open）。数据全部来自架构子 agent 的返回消息。

3. **Phase 2 中逐条提交 finding**：每确认一条（或一个域审完一批），立即用 Edit 把 vuln-card 插入报告 #vulnList 的「finding 块结束」锚点之前，按 critical → high → medium → low 插到正确位置（插在已有同等级卡片的最后一个之后）。追踪完一条链就落一条结论，不要攒到全扫完。

4. **Phase 3 后提交攻击链与误报**：攻击链卡片插入 #chainsView 锚点前（`data-fid` 为 CHAIN-1…；无链则在该视图写明无可组合链及原因）；误报卡片插入 #fpView 的「误报块结束」锚点前（`data-fid` 为 FP-1…，含驳回原因）；复核中调整等级/置信度的 finding 直接修改对应卡片（data-sev、类名、sev-tag 文本、疑似标签）；无误报时删除 #fpView 及对应标签按钮。

5. **收尾**：更新头部「完成时间」与页脚时间戳。自检：
   - 报告里不得残留任何 `【` 占位符（「完成时间」与页脚时间戳尤其容易漏）
   - 模板文件（report-template.html）保持原样未被改动
   - 攻击链与误报视图按第 4 步处理完毕
   - 最终输出按「对话输出规格」四块给出 —— 「分域」一行必须把**实际执行的域**逐个交代，这是防止静默丢域的凭据
   - **清理临时文件**：删除审计过程中产生的所有非交付物，运行目录最终只剩 `安全审计报告-<项目名>.html` 一个文件

**模板是只读骨架，严禁直接 Edit 模板文件。** 增量提交只发生在报告文件上。

### 卡片写法

每条 finding 一个 `<div class="vuln-card vuln-{severity}">`，插在 #vulnList 锚点前：

- 必须带三个属性：`data-sev`（critical/high/medium/low）、`data-stage`（该 finding 归属审计域：rce/injection/file/auth/business/xss/config/other）、`data-fid`（V-001 依次编号）；confidence=suspected 时加 `data-confidence="suspected"`
- 卡片字段块依次为：描述 / 定级评判 / POC（带复制按钮）/ 预期响应 / 位置 / 调用链 / 证据 / 修复建议
- 字段映射（schema → HTML）详见 [finding-schema.md](references/finding-schema.md) 末表
- **计数标签、汇总面板、漏洞清单表、修复建议列表由页面 JS 从卡片 DOM 自动生成，不要手填** —— 只写卡片，其余交给脚本

### 生成纪律

- **CSS 与 `<script>` 一律不碰**：报告是 `cp` 出来的副本，样式与脚本天生是模板原文 —— 不要改动、压缩、省略，也不要「顺手整理」缩进
- **所有正文内容做 HTML 转义**：`&` → `&amp;`、`<` → `&lt;`、`>` → `&gt;`、`"` → `&quot;` —— POC、代码证据里的 `<token>`、`->`、引号都必须转义，否则浏览器解析错乱
- 配置类 finding 无 HTTP POC 时省略「预期响应」块，「POC」字段写发现位置与内容
- 覆盖度说明**不写入 HTML**（模板无此节）—— 只出现在对话输出里

## 对话输出规格（严格照此，不要扩写）

**HTML 报告是唯一交付物。审计结论只写进报告卡片，不在对话里复述** —— 漏洞描述、POC、证据、修复建议、调用链一律不要出现在对话中。

审计过程中**不要逐步播报**（不写「正在派发 7 个域」「injection 域返回了」「开始复核」）—— 进度由任务清单承载。只在三种情况下输出文字：

1. **开场一行**说明本次执行范围（如 `模式：全量扫描｜目标：D:\web`）—— 仅在范围由自然语言推断得出时写，带完整参数调用时省略
2. **需要用户决策时**（缺路径要问、无参数加载要给使用说明）
3. **最终收尾**，按下方四块格式

最终输出固定为四块，总长控制在 20 行内：

```
报告：<报告文件绝对路径>
计数：共 N 条（critical A / high B / medium C / low D；confirmed X / suspected Y）｜攻击链 Z 条｜误报剔除 W 条
分域：rce N ｜ injection N ｜ file N ｜ auth N ｜ business N ｜ xss N ｜ config N
缺口：<未覆盖的攻击面，或「无」>
```

四块的硬性要求：

- **分域**一行写完，把实际执行的域逐个列出并给数字。零 finding 的域必须区分：已审完写 `0(已覆盖)`，没审到写 `0(缺口)`，规划阶段跳过的写 `跳过:<理由>`
- **缺口**只列未审到的攻击面，一条一行，没有就写「无」
- 已经输出过 finding 就**不能**写「未发现漏洞」—— 自相矛盾会误导读报告的人
- 串行执行（无子代理能力）追加一行：`提示：本次串行执行，后段域深度可能低于前段`

除上述内容外不要再写小结、建议或感想。用户要看的是报告，不是对话。

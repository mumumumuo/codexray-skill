# 业务逻辑漏洞审计

> **风险等级**：🟡 高危 — 可造成资金损失/业务破坏
> **域 ID**：`business`

## 审计范围

- **流程绕过**：跳过中间步骤直接调用最终接口
- **高并发 / 竞争条件**：重复提交、TOCTOU、库存超卖
- **金额或数量篡改**：负数、零、超大数、小数精度
- **状态机制绕过**：状态字段可控、跳过状态校验
- **业务规则绕过**：优惠券叠加、积分倒挂、空订单
- **幂等性缺失**：重复支付、重复发券
- **SSRF**：内部接口接收用户提供的 URL 并发起请求（`http.Get(userInput)` / `requests.get(userInput)`）
- **DoS / 资源耗尽**：未限制大小的循环 / 文件 / 列表操作

## 任务要求

- 分析核心业务逻辑和状态流转，画出状态流转图（文字描述）
- 检查关键操作顺序，找出可跳过的中间步骤
- 对所有数值参数检查上下限：
  - 是否可为 0
  - 是否可为负数
  - 是否可超出业务合理范围（如订单数量 999999）
  - 是否存在小数精度问题
- 检查事务保护：多步操作是否原子性、并发是否加锁
- 检查 `//todo` 和被注释的代码（隐藏逻辑、未完成的校验）
- 检查所有出站 HTTP 请求是否使用了用户可控的 URL（SSRF）
- 枚举业务逻辑漏洞利用点

## 输出要求

每个漏洞必须说明：

- **攻击前提**（需要的前置条件）
- **利用步骤**（详细操作序列）
- **被破坏的业务约束**（明确哪条业务规则被违反）
- **影响结果**（金额损失、数据损坏、服务不可用等）
- **必须提供 raw 格式 HTTP 数据包**（条件竞争 / 多接口联动给完整 Python 脚本）

## 边界

业务流程绕过 / 金额或数量篡改 / 状态机绕过 / 重复支付或重复发券（幂等性）/ 条件竞争 / SSRF（业务层用户输入→URL）/ 资源耗尽 DoS 归本域。

以下类型**绝对不要**输出 finding（见 [domain-boundaries.md](../domain-boundaries.md)）：

- **SQL / NoSQL / PromQL / LogsQL 注入**（即便出现在业务 handler 里）→ `injection`
- **命令注入 / 反序列化 / 模板 SSTI** → `rce`
- **文件上传 / 下载 / 路径遍历** → `file`
- **鉴权机制本身的缺陷**（无认证、JWT 空密钥、密码哈希弱）→ `auth`（注意："已认证用户利用业务逻辑漏洞越权操作其他用户数据" → 本域；"端点本身无认证保护" → auth）
- **XSS** → `xss`
- **CORS / TLS / 调试模式 / 硬编码凭证** → `config`

**特别说明**：SSRF 归本域，因为是"业务层未校验用户输入的 URL"——属于输入校验层面的业务逻辑缺陷。但 TLS 证书校验缺失（`InsecureSkipVerify`）→ config 域，那是配置层问题。

看到上述越界类型时，在 COVERAGE 简述即可，例如："在 api/datasource.go:233 的 searchViewLogsContent 接口发现 SQL 拼接，建议 injection 域关注"。

字段 schema、定级原则、POC 要求见 [finding-schema.md](../finding-schema.md)。

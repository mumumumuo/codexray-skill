# 认证授权边界分析

> **风险等级**：🟡 高危 — 可绕过访问控制
> **域 ID**：`auth`

## 审计范围

- 未授权访问（端点未被任何认证机制保护）
- 认证绕过（认证机制本身存在缺陷）
- 水平越权（用户 A 可操作用户 B 的资源）
- 垂直越权（普通用户可操作管理员功能）
- 权限提升（注册即管理员、角色字段可控等）
- 功能级访问控制缺失

## 必须完成的动作

### 1. 🔒 认证配置 vs 端点清单 交叉比对

- 从认证中间件 / 拦截器 / 装饰器配置中提取：哪些路径被保护、哪些路径被排除
- 与 Phase 1 架构子代理给出的全部端点清单逐一比对
- **列出所有未被任何认证机制保护的端点**

### 2. 🔑 认证绕过模式检查

- 对每个**受保护**的端点，检查 Handler 内部是否从 Session / Token 中获取了当前用户身份
- 检查获取到的用户身份**是否实际用于后续的数据查询**
- ⚠️ **关键模式**：从 token 中拿到 `userId`，但查询时用的是 `request.userId`（从请求体取）—— 等于没鉴权

### 3. 👤 数据归属校验检查

- 对每个根据 ID 操作数据的接口（详情/编辑/删除），检查资源 ID 是否与服务端获取的 userId 关联
- 是否直接使用客户端传入的 ID 操作数据，未校验该数据属于当前用户

### 4. 🎫 会话 / Token 安全性

- 密码存储算法是否安全（MD5/SHA1 不安全，bcrypt/argon2 安全）
- 登录失败是否有次数限制
- 会话固定 / Token 泄露风险（Token 是否包含敏感信息、Cookie 是否带 Secure/HttpOnly）
- JWT 签名密钥是否硬编码、是否为空（配置文件和源码中搜索签名密钥）

### 5. 🚪 注册接口提权审计

- 注册接口是否允许用户自定义角色 / 权限字段
- 角色字段是否在服务端强制覆盖

## 输出要求

- **未授权端点清单**（含完整代码追踪）
- **越权漏洞清单**（含水平/垂直越权的具体表现）
- 每个漏洞的完整 HTTP 数据包
- 重点说明「触发漏洞所需的最小权限」（对应 `min_privilege` 字段）

## 判定纪律

- 端点未在中间件白名单内，但框架默认全局拦截 → 先确认框架的默认行为，再判断是否真的裸奔
- 健康检查、登录、静态资源等设计上匿名的端点，不算未授权访问漏洞
- 「无认证保护」与「认证存在但校验逻辑有缺陷」是两条不同的 finding，不要合并
- 资源 ID 来自 Token/Session 且做了归属校验 → 不是越权

## 边界

未授权访问 / 越权 / 注册接口提权 / 密码存储算法 / JWT 签名密钥配置 / Session 管理 / OAuth 流程缺陷归本域。

以下类型**绝对不要**输出 finding（见 [domain-boundaries.md](../domain-boundaries.md)）：

- **CORS 配置错误**（`Allow-Origin: *` + `Allow-Credentials: true` 等）→ `config`
- **TLS 证书校验**（`InsecureSkipVerify`）→ `config`
- **调试接口暴露**（pprof / actuator / swagger）→ `config`
- **数据库密码 / 第三方 API Key 硬编码** → `config`（注意：JWT 签名密钥、Session 加密密钥仍归本域）
- **SQL / NoSQL 注入**（即便出现在鉴权代码里）→ `injection`
- **业务逻辑流程绕过**（跳过中间步骤、状态字段可控）→ `business`
- **SSRF**（鉴权代码里如果有 SSRF 也归 business）→ `business`

看到上述类型时，在 COVERAGE 简述即可，例如："在 middleware/cors.go:12 发现 CORS 配置 `Allow-Origin: *` 与 `Allow-Credentials: true` 同时启用，属 config 域"。

字段 schema、定级原则、POC 要求见 [finding-schema.md](../finding-schema.md)。
